# Contributing to the Chivalry 2 Mod Wiki

Publish reusable procedures and findings. Keep personal development logs in a separate private knowledge base.

## Content boundary

- Exclude usernames, personal filesystem paths, machine names, server addresses, credentials, private repositories and installation receipts.
- Exclude custom mod settings, release histories, private tool APIs, helper-script commands and links that require another workspace folder.
- Do not use private pipeline numbering or work-item codes ("Script 2", "stage 3", issue numbers). Name each step by what it does (for example collection, base conversion, completion), so a reader without the original workflow can follow it.
- When a mod demonstrates a general lesson, explain the mechanism, version, validation method and limitation without requiring that mod.
- Standard Unreal package paths, documented SDK classes, public tools and reader-defined path placeholders are appropriate.
- Do not copy private standing permissions into public procedures. A guide does not authorize installation, process termination, source changes or publication.
- Keep game assets, captures containing identifying data, and raw extraction bundles out of documentation releases. This folder distributes prose, not game content or third-party tools.

## Evidence

Distinguish documentation/source inspection, editor execution, cold saved-asset validation, archive verification, and shipping-game tests. State which level supports a claim. Test one feature at a time and record versions and remaining uncertainty.

For a reusable failure, describe the symptom, established cause or hypothesis, fix, verification and remaining limit. Replace superseded instructions in the guide. Do not carry a historical failure forward as a universal current limitation.

Proposed architecture must be labeled as a proposal. Successful saving, matching hashes, actor counts or an empty work queue do not establish complete behavior or visual fidelity.

## Review before sharing

1. Read every changed page for personal details and hidden dependencies; redacting drive letters alone is insufficient.
2. Check relative links resolve inside this folder. Public links must not target private repositories or local files.
3. Search for absolute paths, account identifiers, private helper names, mod names, deployment logs and stale claims of permission.
4. Verify examples use reader-supplied roots and standard/public facilities. If automation needs unavailable tooling, describe the manual operation or algorithm instead.
5. Confirm evidence qualifiers survived editing. Keep this README's topic index current.

The initial edition consolidates lessons rather than mirroring the private history tree. Personal build counts, hashes, tester routes and release plans are intentionally absent. VR research had no established runtime result and is not presented as a working setup.
